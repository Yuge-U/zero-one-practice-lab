# OneDrive同期遅延・保存継続の修正候補 1.3.3

対象: Yuge-U/zero-one-practice-lab。基準 main: 18c7c823508934147d02e3455a826bc84d653692。修正ブランチ: fix/sync-latency-recovery。

## 症状と再現

利用者から「OneDriveと同期中から変わらない、または同期失敗」「背景へ移ると落ちる」との報告。端末機種・ブラウザ・OSによる強制終了の有無は未確認。

1. 1.3.2のAppServiceはすべての要求を一つのPromiseキューへ入れる。応答しない同期を先行させる再現試験で、後続のsavePlanも完了しないことを確認。
2. WorkerBridgeでは同期の通信期限切れもfail()を呼び、全要求を拒否して保存機能を停止する。制御した時計の試験でonFatalが呼ばれることを確認。実OSによる終了の再現ではない。
3. 同期は既送信検証と前後のpullで同じ履歴を順次読み直す。ファイル本文の前にメタデータを二重取得し、変更のない本文も繰り返しダウンロードする。
4. OneDriveCloud.get()は本文取得の通信例外までJSON破損に変換する。通信障害をNETWORKとして返す回帰試験を追加。

これらはコードと模擬試験で確認した不具合。利用者の実アカウントで発生した全症状の原因を断定するものではない。

## 変更

- awaitを持たない端末DB操作を通信待ちから分離。端末操作同士は順序を維持し、close/restoreは先行する両方の処理を待つ。
- 同じ世代の同期要求だけを共有。保存を挟んだ同期を落とさず、同期中に追加された未送信保存は成功後に再同期する。失敗後に自動ループしない。
- 通信要求の期限切れで保存Worker全体を停止しない。端末書込みの結果が不明な場合の停止と自動再保存禁止は維持。
- 履歴の読込みを最大4要求ずつに限定して並列化。失敗時も同じバッチの終了を待ち、次の同期と重ねない。
- Graphで取得したばかりのメタデータを利用。Graphで毎回存在とeTagを確認し、同じ版の本文だけをWorker内で再利用。キャッシュは最大8MiBで、永続保存せず、トークンや署名URLを含めない。eTagがなければ従来通り本文取得。
- 本文・ハッシュ・所有者・消失・送信後読戻しの検査を維持。通信例外はデータ破損に置換しない。

DBパス、スキーマ、本人とゲストの境界、OneDriveフォルダー、アプリID、Microsoftの権限・登録設定は変更していない。写真・動画・参考資料の保存形式も変更していない。Webサイトデータの削除を手順にしていない。

比較対象 basketball-tactics-board の1_App/js/onedrive-storage.jsは読み取りのみ。比較対象では4件ずつ並列取得し、更新日時が同じ項目を再利用していた。PRACTICEではデータ検証を残し、本文の再利用はeTag一致を条件とした。同一ドメインの認証キャッシュ設定は今回変更せず、前版の本人選択と再認証検査を維持。

## 試験

- 単体: 224件合格、失敗0、skip0。既存213件と追加11件。
- 新規ブラウザ: Chromium / WebKit各6件、計12件合格。同期中の追加保存、制御した通信期限切れ後の保存、visibilitychange競合、保存後同期失敗と再試行、未送信状態からの再読込み回復、変更のない本文の再取得抑止。
- 既存ブラウザ228件と新規12件、計240件合格。通信18、保存表示22、認証接続36、今回12、基本画面22、保存・コピー30、旧版更新2、分類28、参考資料34、写真動画36。全既存ゲートを保持。
- 実SQLite/OPFSと本体Auth/Worker/Graph処理を使用。MSALとOneDriveは合成。背景移行はイベントと時計の制御であり、実端末のOS終了ではない。

## 残る確認

実Microsoftアカウントでの所要時間、利用者の端末での背景移行・OS停止・復帰は未確認。保存確定前の入力をOSが破棄する場合まで回復できるとの保証はしていない。データが大量の場合は端末DB処理自体の所要時間も別途観測が必要。
